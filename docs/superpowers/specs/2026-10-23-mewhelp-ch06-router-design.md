## 1. 目标、已批准边界与基线

将 ch05 占位分流器升级为支持同会话多轮理解、八选一意图分类及确定性退款/售后流程的正式实现。验收重点是物流→退款→物流切换、忠实消解指代、可解析 JSON、未知问题兜底，以及浏览器缺订单号点选后继续原流程。

用户原始约束：不训练分类器、不做跨会话记忆、不增加组件、不换既定栈、不在入库侧复制知识；前端采用 Vibe Coding，不套 brainstorm/TDD/code review。Prompt 和数据任务使用标注样例/评估集替代 TDD，后端可单测行为按 TDD。

用户本轮裁决：「批准，另附留痕文件已更新」，针对上轮提出的模拟订单、演示退款提交边界。申请记录具体承载方式在本设计明确为复用现有 tickets 售后工单；不创建退款表，不执行退款资金动作，不把提交成功说成退款获批。

真实产品基线为 `E:/MewHelp AI/.worktrees/ch05-workflow-agent`，根目录仍为 ch04。ch05 有大量未提交实现与修复，不能从其 HEAD 新建空工作树而遗漏这些内容。实施前按 using-git-worktrees 技能确定保留基线的隔离方式，不自动提交或丢弃改动。根目录本 spec 与 dev-notes 为审批入口，执行后在实际产品工作区同步对应文档。

## 2. 方案比较与推荐

1. 推荐：显式图节点实现理解、分类、订单选择/读取、查询扩展、政策检索与证据闸，再进入主力 Agent。等待选择使用LangGraph原生interrupt()暂停，点选后同一thread_id通过Command(resume=...)继续；沿用官方SQLite检查点及现有会话锁。
2. 全部交给主力 Agent 自主选工具：改动少，但无法确保先订单后政策，遗漏关键步骤难以从结构上防止，不采用。
3. 原生interrupt/Command恢复：依据用户补充裁决，已并入推荐方案并作为必须机制。原先不采用的结论作废；须明确处理节点重执行。

继续使用现有 LangGraph、官方 AsyncSqliteSaver、LangChain、FastAPI、SQLAlchemy、MySQL、Milvus 及静态聊天页，不新增服务或依赖。

## 3. 多轮指代与 Query 改写

在分类前由一次 LLM 调用结合裁剪后的同会话历史及当前原话，合并做指代消解与口语归一化。历史仅作数据，不接受其中对分类器/系统的命令；沿用完整工具消息配对、历史预算和 usage 计量。

内部理解结果包含 standalone_question、是否成功消解及经引用验证的订单关联信息；不与用户规定的意图/扩写 JSON 混用。最终字段及长度限制在计划中固定。订单关联只能来自当前用户原话、明确历史引用或服务器确认的点选状态，不能信任模型自由生成的订单号。

原话已完整且表述明确则逐字透传，含明确指代的完整问题不为“润色”重写。口语模糊问法可归一化，但保留 SKU、订单号、否定、时间、金额、条件和用户诉求。语义上有多个候选指代时不强选，保留原话/歧义标记。订单缺失通过选择器解决，其他需求澄清由 Agent 完成，分类器不追问。

原问题、独立问题分开存 State，MySQL 用户消息保留原话，不用改写覆盖归档。后续检索直接使用本轮理解结果，不再经 ch04 单轮改写器重复模型改写；ch04 独立检索入口与 query_faq(keyword) 的兼容契约保持。

## 4. 意图分类 Prompt 与模型

选择题枚举：物流、订单、商品咨询、退款退货、售后、投诉、闲聊、其他。仅输出 `{"intent":"退款退货","confidence":0.96}` 两字段；禁止额外字段、解释、Markdown。confidence 必须为有限的 0～1 数值，不把模型自报分数称为校准概率。

Prompt 四件套：选择题定义、严格 JSON 形状、边界 few-shot、其他兜底。few-shot 至少覆盖订单1001能退吗→退款退货、退款到账进度→售后、包裹位置→物流、运费规则→商品咨询、强烈投诉→投诉、普通问候→闲聊、月球采矿许可→其他，以及引用先前商品后改变诉求的例子。当前消息诉求优先，不继承上轮意图；投诉明确优先，多业务无投诉时以当前主要诉求分类。

合法但含糊/库外怪问题进入其他，由固定简短文案说明可服务范围并邀请重述；不硬塞商品咨询，不用常识回答。低置信度初始建议阈值0.7，可配置并以评估集核验；不足则其他。结构非法允许预算内一次格式修复，仍失败输出系统生成的其他/0并记录结构失败。供应商不可达或超时走明确服务错误，不冒充语义兜底。

默认使用同一已配置聊天上游的主力大模型，分类模型名可独立配置且不修改真实 .env、不增加供应商。质量通过固定评估证明，不能因当前模型默认名含 flash 就宣称足够。本章只执行主力大模型默认分类；成本降级仅保留配置种子intent_small_model=None、intent_escalation_threshold=0.7，不实现小模型调用、置信度升级或模式切换开关，即使填写种子也不改变执行路径。未来章节才实现“小模型先判→低分升级主力一次”。intent_min_confidence=0.7是当前大模型低置信度归其他的阈值，不能混同未来升级阈值。本章不训练或购买/切换模型。若当前上游模型无法满足 JSON/准确率，先报告证据请用户裁决，不自行换技术方案。

## 5. 路由及确定性退款/售后子流程

物流/订单→现有业务 Agent；商品咨询→单查询知识检索及既有证据闸；投诉→保留两个独立操作；闲聊→固定回复；其他→独立固定兜底。退款退货与售后均进入同一确定性子流程，不能因订单号、模型建议或退款状态问题绕过政策检索。

顺序固定：理解→分类→确认订单关联→读取订单数据→扩写→多查询政策检索并合并→证据闸→主力 Agent 根据订单和条款判断/解释。Agent 不再决定是否执行前置订单和政策步骤。只有拿到可用政策才进行资格判断；不能用订单状态或模型常识推断退货资格。

本章按用户描述，退款/售后入口均先关联订单；简单商品 FAQ 不扩写。不把“退货政策通问”暗中另开绕过该子流程的出口。若产品日后需要无需订单的纯退货政策问答，再单独裁决。

已有明确订单号或可唯一验证的历史订单关联则直接读；有多个订单或仅有商品泛指，显示订单选择器。不以最近访问订单自动代替指代判断。读取失败不继续检索/判断；返回服务错误或选择可用订单。订单字段缺失时 Agent 说明缺少签收日/商品状况等，不能捏造资格；需求澄清保留在 Agent，退款原因永不由对话强制追问。

## 6. 模拟订单与待选状态

提供小型、固定、可重启复现的演示订单集，包含订单号、商品、状态、金额、下单/签收时间及可用条件字段；明确演示数据。卡片和 query_order 对演示订单使用同一数据源，相关物流工具结果不与订单状态冲突；不把随机生成的任意订单当作当前用户真实购买列表，不冒充真实订单所有权校验。

缺订单号时在独立准备节点生成服务器selection_id及候选快照，绑定session_id、原请求、独立问题和intent，提交到检查点；下一await_order节点调用interrupt(payload)原生暂停。runtime从updates中的__interrupt__或StateSnapshot.interrupts提取并发送order_selection，不把暂停当异常/完整退款终态。前端不展示分类JSON或内部提示词。

点击仅提交session_id、selection_id、order_id，后端持有会话锁并从最新检查点确认真实待处理中断、候选及请求仍有效；通过同一thread_id执行Command(resume=已验证选择, update=新预算及continuation关联)恢复await_order。interrupt返回值仍须在节点内防御性校验，随后进入读取订单；不重新分类、不重插原消息、不用aupdate_state(as_node=...)伪造已完成节点跳转。等待不消耗原90秒时限，恢复调用计量单独留存关联。

新聊天消息使未选的旧选择器失效；已完成选择重复提交不重跑子流程，返回已处理状态；并发点击只允许一个获胜。检查点已接收但执行中断则标记中断并提示重新发起，不自动重放。不要求逐 token 断线续传。

重启可通过现有会话状态读取入口（或新增只读恢复入口）恢复待选卡片及操作状态；恢复后再次验证候选。session_id 仍为演示会话标识，不宣称身份鉴权。

## 7. 检索侧多查询扩写

仅退款退货/售后子流程在拿到订单后调用扩写模型，强制输出 `{"queries":["…","…","…"]}`，只有 queries 一个字段。生成2～3条互补政策查询，加上原独立问题作为保底，最多4条实际检索；按申请条件、例外/商品状况、流程/到账时效等与当前诉求相关角度展开，不添加用户未说的瑕疵或承诺。

保留原独立问题的限制条件，订单上下文仅用于检索相关性，不把客户姓名/地址等多余数据发给嵌入或写入日志。空串、重复、超长、额外字段或格式错误均校验；预算内一次格式修复，仍失败以原问题检索并标记扩写降级，不编造多查询成功。

逐条使用现有检索策略/过滤器，强制选政策材料。MySQL chunk_id 去重，候选来源取并集；用倒数排名合并候选，再由现有 reranker 对原独立问题统一重排并取Top10，避免把不同查询的 raw score 直接比较。最终引用统一编号，对应唯一 MySQL 原文。扩写不写库、不复制知识、不触发建库。

服务错误不得用其他查询的成功结果掩盖为完整流程成功；既有知识缺口拒答/问题池语义保留。评分闸沿用部署阈值，但本章检索编排变化须真实评估，不能把 ch05 校准自动当新流程质量证明；不覆盖冻结 profile 或伪造 identity。若修改触发 profile code_hash 失效，按既有规则创建独立校准产物并记录。

## 8. 退款申请表单与持久化

完成订单及政策分析后提供“提交演示退款申请”入口，表单显示只读订单、用户从固定下拉选原因，可选补充说明。固定原因建议：不喜欢/不合适、尺码问题、商品质量问题、与描述不符、其他；原因选择不代表原因成立，不接受未列举值。未知资格可提示待审核，拒绝作退款获批承诺。

仅用户点击确认提交后，以服务器 action_id 绑定的订单+合法原因+补充说明构造 description，复用现有 create_ticket 的售后类型保存记录。conversation_id 继续系统注入，不接受客户端任意替换订单/关联主键。不修改已有通用工单确认接口语义，新增独立退款表单提交入口和校验。

成功返回工单号并明确“演示申请已提交，待审核；未执行真实退款”。未确认/取消不写 tickets。重复提交返回原结果；写入结果不确定时沿用 creating/uncertain 语义，禁止自动重试，提示核实。MySQL 与 SQLite 不保证跨库原子或 exactly-once。

## Ruling 2026-10-23：订单选择必须使用LangGraph原生中断

用户关键原话：「缺订单号时弹出订单选择器，点选后的子流程接着走，机制应当使用langgraph的interrupt，你自检一下」。此裁决覆盖此前应用层等待/手动as_node续跑设计，无需另询是否改用用户已指定机制。

当前Task5尚未实施；runtime旧_interrupt只是异常状态标记，不能当作原生interrupt。await_order节点恢复时从头执行，故selection_id/候选准备须在前一已提交节点，不在interrupt前生成随机ID、调用模型、查订单、写工单或归档消息；不以宽泛except吞GraphInterrupt。保持中断和SSE断线错误语义分开。待选期间其他actions的保存不得通过旧save_actions(as_node=log_result)意外消费/取消原生中断，须专项回归覆盖。新消息使旧选择失效，resume只允许当前活跃中断；重启从官方SQLite恢复pending interrupt。

Context7核对官方 https://docs.langchain.com/oss/python/langgraph/interrupts；锁定版支持Command(resume,update)及StateSnapshot.interrupts。临时SQLite表征测试验证同thread重启后恢复、等待节点重执行而准备节点不重放，1passed；此结果仅验证机制，不是产品续跑功能验收。


## Ruling 2026-10-23：意图降级仅留配置种子

用户关键原话：「意图识别的降级路线，本章只做大模型默认，降级留配置种子」。本章不实现可启用的小模型/升级分支，新增两个纯未来配置种子，默认值None/0.7；填入种子不构建/调用小模型。主力大模型自身一次JSON格式修复不算小模型升级；大模型低分归其他不再发另一模型重判。独立主力型号intent_model继续沿用同一上游，名称或参数规模不能仅凭别名猜测。
