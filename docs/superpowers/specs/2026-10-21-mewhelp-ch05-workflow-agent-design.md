# ch05：确定性 Workflow 与核心 ReAct Agent 设计

日期：2026-10-21设计定稿；2026-10-22实施finish。整体设计、书面spec与实施计划均获用户批准，Native Tasks1–9完成，最终630项全量通过；真实验收与限制见reports/ch05/summary.md，最新入口docs/CH05_CURRENT_PROGRESS.md。

## 1. 目标与验收边界

将现有单轮工具聊天升级为 LangGraph 确定性工作流，核心业务节点使用可多步调用工具的 ReAct Agent。先手写无 Agent 编排框架的循环，理解调用、执行、观察、收敛，再以 LangGraph 重构同一行为。两步均复用现有模型适配和业务工具；“裸循环”不要求重写 HTTP 客户端或工具 schema。

这是面向生产架构演进的本机演示阶段，不宣称整套系统已经满足生产部署要求。官方 SQLite checkpointer 是用户明确选型，采用本机单进程运行；现有业务查询仍是 Mock，现有无鉴权边界不因本章自动消失。所有演示与真实写入均面向核实后的本地环境。

本章完成以下可观察行为：政策问题必经检索和前置证据闸；业务问题由 Agent 调工具；投诉不进 Agent，只给用户可选操作；闲聊直接固定回复；组合问题有两步以上工具观察与决策。State 贯穿图并可跨进程重启恢复已完成会话状态。

## 2. 用户裁决与历史契约变更

3. 用户对整体设计回复「通过」：确认模型/工具拆分循环节点、七类固定分流、6 次工具/12,000 tokens/90 秒的可配置初始预算、两个独立按钮及工单确认交互。

## 4. 演进顺序与模块边界

第一阶段产出可运行的裸循环示例及测试/演示证据：模型给工具调用则由现有执行器执行，回灌匹配的 ToolMessage，再请求模型；无工具调用则结束回答，缺信息则追问；预算与副作用限制同正式图。保留一个简洁教学入口，不维护第二套线上聊天流程或复制业务工具实现。

第二阶段将相同行为重构为图：`agent_decide` 选择工具、追问或回答，`agent_tools` 执行只读业务工具并回到决策，`agent_answer` 输出最终正文。这里的决策/观察均指外部工具调用记录，不索取、记录或展示模型内部思维链。采用显式节点循环，而非将整个 while 循环隐藏在一个不可观察的大节点里。

预期职责划分：图状态/路由/节点、Agent 预算及循环、SQLite 生命周期、可选操作服务、SSE 适配分别独立；具体文件和任务拆分由实施计划确定。`app/main.py` 保持入口，`app/chat_service.py` 接线新编排，现有 `app/tools.py`、`app/executor.py` 继续提供业务工具；不无关重构 KB 管线和后台作业。

## 5. 工作流与固定分流

公共前缀为：载入 State → 指代消解 → 意图识别 → 代码路由。

指代消解节点将用户原话原样透传，保留 `raw_question` 与 `resolved_question` 两字段，不假装已具备正式多轮指代能力。Agent 仍能看到经现有策略裁剪的历史。

意图识别以简单 Prompt 返回严格 JSON，只允许「物流、订单、商品咨询、退款退货、售后、投诉、闲聊」七值；模型不得直接决定图出口或返回任意节点名。混合问题仍归一个主意图，优先保证政策/条件问题归知识出口，例如「订单1001能不能退」归退款退货；仅查询退款状态归售后，查配送轨迹归物流。明确投诉诉求归投诉，纯客套归闲聊。模型输出非法结构/未知类别按分类服务异常处理，不默认为闲聊绕过知识闸，不无限修复重试。

固定映射在代码中实现：

- 商品咨询、退款退货 → `retrieve_knowledge` → `evidence_gate` → 核心 Agent 或拒答。
- 物流、订单、售后 → 核心 Agent，不做预检索，不走证据闸。
- 投诉 → 固定安抚回复及 handoff/create_ticket 两个可选项，不进 Agent。
- 闲聊 → 固定话术，不调用 Agent 或工具。

所有成功出口经过 `log_result` → END；异常由统一错误处理记录终态，再由 SSE 适配发送 error，不能继续发送 done。日志节点不额外请求模型。

投诉固定话术建议为「很抱歉给您带来不好的体验。您可以选择转人工，或确认创建工单记录这次问题。」闲聊固定话术为「您好，我可以帮您解答古着商品、退换货政策，以及订单、物流和售后问题。」本章不按闲聊内容动态生成文案。

## 6. 知识检索与前置证据闸

知识出口必须执行真实检索节点，复用 `retrieve_result`、ch04 查询处理及证据格式，不用 Agent 自行决定要不要先查 FAQ。政策检索词保留用户问题及必要条件，不用订单号覆盖政策语义；若复用 ch04 QueryPlan，其旧 intent 不得反向修改本章已确定的图出口。

闸门先于 Agent 和任何正文 token。最简判断复用 `retrieval_rejection_reason`：无有效 hit 拒答；hybrid_rerank 使用有限有效重排分数及当前配置阈值，不将 RRF/BM25 分数当概率，也不擅自给其他策略套同一阈值。运行实际 ch04 v2 时显式加载现有冻结 profile（当前值 0.25 是历史已校准结果，实施时核对文件）。该最简闸不宣称能验证所有事实覆盖。

通过时将原问题、带编号证据及来源元数据交给 Agent，沿用既有证据编号/首尾排布能力；退款退货可以继续查询订单，不让查询结果替代政策。知识回答按证据回答，不满足关键条件时可追问或说明不足。

拒答时不调用 Agent，复用现有兜底文本，通过既有 `record_low_confidence` 写入用户原话、真实 conversation_id、`retrieval_low_conf` 和简短理由。每个正常请求终态写一次，检索内部重试不写池；不承诺断线重发跨请求去重。写池失败明确报错，不虚报已记录。

检索、嵌入、重排服务不可用属于服务错误，不记为正常低置信度知识缺口。业务数据出口没有证据，不执行此闸；若业务工具阶段自行调用现有 query_faq，该次结果不能作为绕过先检索规则的入口，必须遵守其证据约束，不将业务出口升级成另一套隐式预检索流程。

## 7. Agent 循环、预算与工具安全

业务能力只复用现有 query_order、query_product、query_logistics、query_faq；不新增业务工具。create_ticket 保留工具实现给用户确认入口复用，Agent 执行路径禁止执行它。模型即便输出 create_ticket 调用，也只能转为可选建议并回灌“尚未创建，需用户确认”的结果；伪造/未知工具不得触发执行。

Agent 可提供 handoff、create_ticket 或两者的结构化建议。建议通过编排控制元数据表达，与正文和业务工具执行分开；控制信号只描述选项，不写业务数据。可用只供编排消费的控制 schema 实现，不把它算作新增业务工具，不根据正文子串猜测用户已确认。具体模型绑定方式在实施计划中按 Context7 与锁定接口确定。

一次模型决策最多执行一个只读业务工具。即使模型返回多个调用，也逐一返回匹配的结果/明确未执行状态，不能留下未配对 tool_call，也不能偷偷并行执行超出本轮预算的操作。下一步根据工具结果决策；简单问题一查即答，组合问题可先查订单再查物流，缺订单号则追问，不捏造参数。

初始可配置预算：每用户轮最多 6 次实际业务工具调用，累计模型输入输出 12,000 tokens，整轮处理 90 秒。整轮模型预算包括分类、检索中必要模型查询处理、Agent 决策及回答调用；不同模型可得 usage 汇总，不只统计最后一次生成。调用前估算输入/工具 schema 与剩余输出，限制本次输出额度；usage 不可得时记录估算值及口径，不声称准确计费或绝不超真实 token。

次数/估算预算耗尽时确定性停止并说明，禁止再请求模型生成收尾。使用独立模型决策次数上限与图 recursion_limit 兜住无工具的控制循环；具体与 6 次工具所需节点数匹配，不误把正常六步流程截断。总时限覆盖检索和模型调用；同步工具线程超时后不能强杀的现有限制如实保留，不能声称底层调用一定停止。只读重试沿用执行器规则，工单写入不进入通用自动重试循环。

## 8. 流式正文、引用与 SSE

保留 `/chat` 请求与 token/tool/done/error SSE 契约，新增 actions 元数据帧。tool 帧仍提供 start/end，前端能辨别顺序多步调用；只展示工具名与状态，不输出含敏感数据的参数。

决策阶段不发布正文，工具调用 JSON、意图 JSON、控制元数据均不作为用户文本。决定回答或追问后进入 `agent_answer`，使用禁止业务工具调用的模型配置实时发送正文 token，避免边发“答案”边又决定调用工具。该回答调用计入预算，首次 token 在整篇生成完毕前可见；不得将完整缓冲再分片冒充实时流式。

保留 citations 帧和 MySQL 原文定位接口。实时流式开始前发送本轮可用来源编号映射，仅代表供回答使用的证据，不虚称“已通过全文核验且全部实际引用”。前端只将已知编号渲染为来源入口，允许正文逐步拼接跨 chunk 的编号；不用模型生成 URL。完成后可按正文中实际编号缩小来源展示，但不以此撤回或验证已发布正文。无知识检索结果时不制造引用。

actions 帧形状为 `type=actions`、`items` 列表，每项包含服务器生成的 action_id、kind（handoff/create_ticket）、固定 label；工单建议可带用于确认的 description、ticket_type。不得把模型给的会话主键当可信数据。只在一轮正常结束时启用操作，错误/中断的未完成建议不启用。

流式异常发生后返回通用错误、停止本轮，前端将已有部分正文标为未完成，不把其落库为已完成 assistant 答案。安全日志只记录异常类别，不回传原始异常、连接串或远端响应。日志记录节点路径、意图/出口、工具名及步数、预算、时延、闸门理由、终态和请求关联标识，不记录思维链、完整客户对话或秘密。

## 9. State、SQLite 与 MySQL 分工

State 至少包括稳定消息 ID 的消息列表、session/thread 标识、系统解析的 conversation_id、本轮请求标识、原问题/透传问题、意图/出口、检索结果与来源、闸门结论、工具次数/模型次数/usage/截止时间、终态、可选操作及其执行状态。每轮 transient 字段显式重置，防止复用上轮证据、按钮或预算。

官方 AsyncSqliteSaver 在应用生命周期内持有连接，退出时关闭；文件默认放 gitignored `log/ch05/checkpoints.sqlite`，其 WAL/辅助文件也不入库。State 用可序列化且经过测试的消息/结构保存，不存模型实例、连接或异步迭代器。不会把真正的 :memory: 当作持久化验收。

图检查点是 ch05 运行状态权威；MySQL conversations/messages 保留业务关联和对话归档，KB 原文/工单/问题池仍由现有表承载。首次遇到无图状态的旧会话可从既有 MySQL 消息导入一次，使用稳定 ID 避免重复拼接；之后不在每轮重新将全量 MySQL 历史追加到图。

继续沿用现有 history_token_budget、裁剪与孤儿 ToolMessage 防御，不在本章引入摘要、长期记忆或新上下文策略。持久化归档与模型可见历史视图区分，不通过裁剪删业务历史。

同一会话聊天与工单操作共享串行锁，不同会话可独立处理；只保证单进程内互斥，SQLite 不等价于分布式会话锁。重启验收覆盖已完成会话的延续及待确认选项恢复；未完成轮次标记中断，不在重启时自动重放可能有副作用的动作，不承诺已发送 SSE 的逐 token 续传或两个数据库间原子提交。

## 10. 转人工与工单独立交互

投诉出口总是给两个独立按钮；Agent 建议可以只给一个或两个。按钮绑定对应消息的 action_id，状态分别更新。继续发消息不确认、不取消其他业务操作、不阻塞下一轮，不自动转人工或建工单。

点击「转人工」仅由前端模拟：先展示「已转接人工客服」，再追加「您好，我是客服小猫，请问有什么可以帮您的」。不调 tickets 写入接口，不改变会话后续路由，不宣称真人已接入；同一按钮重复点击不重复追加问候。

点击「建工单」先显示服务器建议的类型和描述，用户确认后才 `POST /api/chat/actions/ticket`，携带 session_id、action_id、confirmed=true。取消不写库。后端从持久化会话找到对应建议，验证 kind/状态，服务端取得真实 conversation_id，复用现有 create_ticket。接口不接受客户端指定 conversation_id，也不信任客户端任意改写工单类型/内容。

普通 `/chat` 不得调用该写入逻辑。没有有效建议、会话不匹配或未确认均拒绝；已成功的相同 action_id 返回原工单结果，不重复写入；前端提交中禁用按钮，失败不虚报成功。创建成功与建议状态持久化跨 MySQL/SQLite 不具备原子事务，进程崩溃可能存在“已创建但确认状态未保存”窗口；这类不确定状态不得自动重试或声称 exactly-once，提示核实。现有无鉴权的 session_id 不是用户身份认证，本章不额外宣称具备多租户安全隔离。

工单工具依然保持原业务实现与会话系统注入；调整旧 docstring/Prompt 中“转人工即建工单”的误导描述属于本章必要兼容修订，不新增业务工具。确认入口对写操作不使用执行器的盲目超时重试，防止一键多写。
