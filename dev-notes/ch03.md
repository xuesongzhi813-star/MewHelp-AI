## 2026-10-19 阶段 1:需求澄清 + 设计(brainstorm)

- **用户原话(需求核心)**:
  - 「我要用 Superpowers 模式给客服系统建知识库,把 query_faq 的内部实现从关键词查表升级成向量语义检索,工具的入参出参契约保持不变。」
  - 五条功能需求:①文档按标题层级结构感知切分、超长递归切、块间重叠裁到最近句号、表格按行切时复制表头;②从历史客服对话挖知识的定时任务,分批喂 LLM、先进暂存表、整体去重入库;③每条知识带 category/questions/answer 拼成向量化文本,另带章节路径/内容类型/是否关键条款/前后块指针四类元数据只存不进向量;④MySQL `knowledge_chunks` 原文权威源 + Milvus `knowledge` 双写,先 pending 再回填 vector_id 转 done,按主键幂等可重跑;⑤在线 Top-K 语义检索替换关键词查表。
  - 技术栈:「嵌入模型 BGE-M3」「向量库 Milvus,MySQL 当原文权威源」;「本章不做关键词召回、混合检索、重排,只跑 dense 向量单路」。
  - 工作要求:「全程走 Superpowers 流程,技能自动触发」「涉及具体库、框架、API 的用法一律先用 Context7 MCP 查最新官方文档」「技术选型是定死的,发现矛盾或走不通停下来问我」「每完成一个阶段就补一段 dev-notes,不许收尾时一次性补记」。
  - 环境补充:「嵌入模型使用 BGE-M3,使用硅基流动的嵌入模型」「MySQL 中的表格我已经建立完毕」。
- **关键产出**:
  - 实测 MySQL:`knowledge_chunks`、`qa_extraction_staging` 两表已存在且为空,字段与需求完全一致(含 `vectorize_status enum('pending','done')`、`prev/next_chunk_id`、`vector_id`);`faq` 13 条。**不需要任何 DDL**。
  - 实测环境:Milvus 未运行(pymilvus 未装、19530 不通);Docker Desktop 已安装,启动后 7.9 GB / 16 CPU;WSL2 Ubuntu 存在。Milvus Lite 官方不支持 Windows 原生(只能 WSL2),向用户说明后裁决为 **Docker Desktop + Milvus Standalone**。
  - Context7 MCP 初始未配置;用户要求先连。执行 `claude mcp add --transport http context7 https://mcp.context7.com/mcp`,`claude mcp list` 显示 ✔ Connected;用户重启会话后 `mcp__context7__*` 工具可用。已用 Context7 核对 PyMilvus `MilvusClient`(create_collection schema/index、upsert、search output_fields/consistency)与 LangChain `with_structured_output` 当前接口。
  - SiliconFlow BGE-M3 官方参数:固定 1024 维、单请求上限 64(实践 32)、OpenAI 兼容端点 `https://api.siliconflow.cn/v1/embeddings`;`dimensions` 参数不支持 BGE-M3。
  - 用户逐项裁决:挖掘 job = 可直接敲命令的 job(不内嵌调度器);去重 = 归一化精确 + 向量相似度阈值;切块 = 500 字 / 100 字重叠;关键条款 = 规则启发式;挖掘范围 = 全部会话按 id 增量;挖掘分类 = 入库时关键词规则;召回阈值 = 可配置;整体方案 = A(MySQL 状态机 + 薄 Milvus 客户端)。
  - 设计文档:`docs/superpowers/specs/2026-10-19-mewhelp-ch03-knowledge-base-design.md`。
- **拒绝纠偏**:
  - 第一版「定时任务形态」问题被用户拒绝,原话:「就设计个命令能启动的job就行,我们可以自己选择部署或者直接执行」→ 改为 CLI `--once` / `--interval`,调度交给外部。
  - 用户否决 LangChain 现成 splitter/VectorStore 路线(方案 B),选择 A:切分规则是硬约束,双写状态机不能被框架封装挡住。
- **翻车返工**:
  - Milvus 运行方式在需求里没写,实测发现本机跑不起来 → 没有自行换方案,停下来问用户,得到 Docker Desktop 裁决。
  - Context7 初次连接后工具未挂进当前会话 → 用户重启会话解决;期间用官方文档 + WebSearch 顶替,并在设计里注明。

## 2026-10-19 阶段 2:设计范围扩展——`/kb` 录入页与 `/admin` 外壳

- **用户原话**:
  - 「补充一个计划知识库录入页 `/kb`:建库这条链搬上浏览器——材料清单与切块预览、手工贴一段文档就能入库、向量化补 pending、检索自测;离线那几个 make 目标也在页面上按。」
  - 「库存闸条…六块」「切块只有一份实现」「双写顺序不许反」「查重按问法 + 正文的指纹」「依赖缺失是一种状态,不是错误」「作业只能跑注册表里的 make 目标,argv 写死,前端只传一个作业名——页面有重跑按钮,但没有 shell」「`kb-mine` 与 `kb-reset` 标 heavy」「录入这类写操作走 API 而不是作业」「后台外壳一次搭好」。
  - 「这里面的文件目录不一定是对的,你要按照当前现有项目的文件目录来安排,而非按照这段设计中的目录,功能贴合一致。」
- **关键产出**:
  - spec 增加 §14 `/kb` 六块 + `/admin` 外壳、§15 作业运行器与 Makefile、§16 API 契约;§4 目录改为 `app/kb/`、`app/api/`、`app/core/`、`app/static/`、`data/kb/`、`Makefile`、`log/`。
  - 统一实现:切块唯一入口 `kb.documents.build_chunks`,材料清单唯一入口 `kb.sources.SOURCES`;页面预览、页面录入、离线 CLI 同源。
  - 指纹由「category|section_path|questions|answer」改为「归一化问法 + 正文」,理由写成 spec §6:同一节多块共用节标题,加入路径会误判,只按问法会误杀。
  - 增加 `kb-rebuild`(保留原文、重置 pending、重刷向量)与 `kb-reset`(破坏性清空)两种恢复路径,避免 Milvus 丢失后无法重刷 done 行。
  - 本机没有 make → 经用户裁决安装 `GnuWin32.Make 3.81`(winget),并把 `C:\Program Files (x86)\GnuWin32\bin` 加入用户 PATH;页面作业与终端 Makefile 同源。
- **拒绝纠偏**:
  - 用户明确要求「文件目录按现有项目安排」→ 没有照抄设计稿里的路径;`app/kb/documents.py`、`app/kb/sources.py`、`app/core/jobs.py`、`app/api/*` 保留,其余落到现有 `app/static/`、`data/kb/`、仓库根 `Makefile`。
  - `make` 缺失没有自行改成 uv 直调,先问用户,得到安装裁决。
- **翻车返工**:
  - 初版 spec 的 `--rebuild` 语义与用户新增的 `kb-reset`(清空知识库)冲突 → 拆成 `rebuild`(非破坏性重刷向量)与 `reset`(破坏性清空),同步改 Makefile、页面按钮与验收项。
  - 初版指纹含 `category|section_path` 与用户「按问法 + 正文」口径不符 → 当轮改正并写明理由。
